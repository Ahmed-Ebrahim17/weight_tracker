# Database Setup Guide: Step-by-Step Explanation

## Overview
This guide explains how we set up SQLite with **Drift** for your weight tracker app. Drift is a **type-safe, code-generated database layer** that makes database operations safer and easier.

---

## Why Drift?

| Feature | Why It Matters |
|---------|---------------|
| **Type-Safe** | Compiler catches errors before runtime |
| **Code Generated** | Less boilerplate, fewer bugs |
| **Reactive** | Can watch for database changes in real-time |
| **Easy CRUD** | Simple, readable code for database operations |
| **Flutter Native** | Built specifically for Flutter |

---

## Step-by-Step Breakdown

### **Step 1: Add Dependencies to pubspec.yaml**

**What we added:**
```yaml
dependencies:
  drift: ^2.17.0                    # Main Drift package
  drift_flutter: ^2.17.0            # Flutter-specific Drift features
  sqlite3_flutter_libs: ^0.5.24     # SQLite for Flutter

dev_dependencies:
  build_runner: ^2.4.12             # Code generation tool
  drift_dev: ^2.17.0                # Drift code generator
```

**Why these packages?**

| Package | Purpose |
|---------|---------|
| `drift` | Core database library |
| `drift_flutter` | Bridges Drift with Flutter's file system |
| `sqlite3_flutter_libs` | Native SQLite implementation |
| `build_runner` | Generates Dart code from our table definitions |
| `drift_dev` | Analyzes our code and generates database code |

**What happens:**
- When you run `flutter pub get`, these packages are installed
- Later, `build_runner` will auto-generate `database.g.dart` from your table definitions
- You don't write raw SQL — Drift generates it for you

---

### **Step 2: Create the Weight Entry Table (Data Model)**

**File created:** `lib/core/database/tables/weight_entry_table.dart`

**What's in it:**

```dart
class WeightEntries extends Table {
  IntColumn get id => integer().autoIncrement()();
  RealColumn get weight => real()();
  DateTimeColumn get date => dateTime()();
  DateTimeColumn get time => dateTime()();
  TextColumn get notes => text().nullable()();
  DateTimeColumn get createdAt => dateTime().withDefault(currentDateAndTime)();
  DateTimeColumn get updatedAt => dateTime().withDefault(currentDateAndTime)();
}
```

**What each field does:**

| Field | Type | Purpose |
|-------|------|---------|
| `id` | Auto-increment | Unique identifier for each weight entry |
| `weight` | Real (decimal) | Actual weight value (180.5 lbs) |
| `date` | DateTime | Day the weight was recorded |
| `time` | DateTime | Time the weight was recorded |
| `notes` | Text (nullable) | Optional comments/notes |
| `createdAt` | DateTime | When this entry was created (auto-set) |
| `updatedAt` | DateTime | When this entry was last updated (auto-set) |

**Why separate date and time?**
- Allows filtering by date easily ("Show me all entries from April 29")
- Allows filtering by time easily ("Show me morning vs evening weights")
- More flexible than storing one combined DateTime

**Why `nullable` for notes?**
- Not every weight entry needs a note
- `nullable()` allows `null` values
- Users can choose to add notes or skip them

---

### **Step 3: Create the Database Class**

**File created:** `lib/core/database/database.dart`

**What it does:**

```dart
@DriftDatabase(tables: [WeightEntries])
class AppDatabase extends _$AppDatabase {
  // This class becomes your main database interface
}
```

**Why this class?**
- This is the **main entry point** for all database operations
- `@DriftDatabase` annotation tells Drift: "Generate database code for these tables"
- Inherits from `_$AppDatabase` (which is generated by Drift)

**What methods we created:**

```dart
// CREATE - Add new weight entry
createWeightEntry(weight, date, time, notes)

// READ - Get data
getAllWeightEntries()
getLatestWeightEntry()
getWeightEntriesLastNDays(7)

// UPDATE - Modify existing entry
updateWeightEntry(id, weight, date, time, notes)

// DELETE - Remove entries
deleteWeightEntry(id)
deleteAllWeightEntries()

// CALCULATE - Business logic
getWeightEntriesCount()
```

**Why this structure?**
- **CRUD operations** are the foundation of database work
- Having them in one place makes the app consistent
- Easy to test and maintain

**The connection:**
```dart
QueryExecutor _openConnection() {
  return driftDatabase(name: 'weight_tracker_db');
}
```
- `driftDatabase()` creates a SQLite database file on the device
- Named `weight_tracker_db` so you can find it for debugging
- This file persists even when the app closes

---

### **Step 4: Run Code Generation**

**Command:**
```bash
flutter pub run build_runner build --delete-conflicting-outputs
```

**What this does:**

1. **Scans** your code for `@DriftDatabase` annotations
2. **Generates** `database.g.dart` with:
   - SQL creation statements
   - Type-safe query builders
   - Data access objects
3. **Creates** the `_$AppDatabase` class your `AppDatabase` inherits from

**Why is this important?**
- You DON'T write SQL manually
- Drift generates safe, optimized SQL for you
- Reduces bugs and makes code consistent

**Example of generated code (you don't write this):**
```dart
// Drift generates this for you:
CREATE TABLE weight_entries (
  id INTEGER PRIMARY KEY,
  weight REAL NOT NULL,
  date DATETIME NOT NULL,
  time DATETIME NOT NULL,
  notes TEXT,
  created_at DATETIME NOT NULL,
  updated_at DATETIME NOT NULL
);
```

### **Step 5: Create the Service Layer**

**File created:** `lib/core/database/services/weight_entry_service.dart`

**What's the service?**
```dart
class WeightEntryService {
  final AppDatabase _database;
  
  // Wraps database methods with business logic
  Future<int> addWeightEntry(...) => _database.createWeightEntry(...);
  Future<List<WeightEntry>> getAllEntries() => _database.getAllWeightEntries();
}
```

**Why add this layer?**

| Problem | Solution |
|---------|----------|
| Scattered database calls throughout UI | Centralized service for all database ops |
| Hard to test UI logic | Can inject mock service for testing |
| Business logic mixed with UI code | Service handles calculations |
| Hard to change database later | Only service needs updating, not UI |

**Example usage difference:**

❌ **Without service (bad):**
```dart
// In 3 different screens:
final entries = await database.getAllWeightEntries();
final entries = await database.getAllWeightEntries();
final entries = await database.getAllWeightEntries();
// If you change the database layer, you update 3 places
```

✅ **With service (good):**
```dart
// In 3 different screens:
final entries = await service.getAllEntries();
final entries = await service.getAllEntries();
final entries = await service.getAllEntries();
// If you change database, update only 1 place
```

**Helper methods in service:**
```dart
getTrendLastNDays(7)        // Returns weight change over 7 days
getSevenDayTrend()          // Convenience method
```
- These encapsulate **business logic** (trend calculations)
- Keeps UI code clean

## Architecture Overview

```
User Interface (Widgets)
        ↓
WeightEntryService (API layer)
        ↓
AppDatabase (Query builder)
        ↓
SQLite Database (Actual data storage)
```

**Each layer responsibility:**

| Layer | Does What |
|-------|-----------|
| **UI** | Calls service to get/save data |
| **Service** | Provides clean API + business logic |
| **Database** | Type-safe queries, CRUD operations |
| **SQLite** | Actually stores data on device |

## How the Data Flows

### **Scenario: User adds weight entry**

```
1. User taps "Log Weight" button in UI
   ↓
2. UI calls: weightEntryService.addWeightEntry(180.5, today, now)
   ↓
3. Service calls: database.createWeightEntry(...)
   ↓
4. Database generates SQL:
   INSERT INTO weight_entries (weight, date, time, ...)
   VALUES (180.5, '2026-04-29', '14:30:00', ...)
   ↓
5. SQLite stores data in file on device
   ↓
6. Returns ID (123) to service
   ↓
7. Service returns ID to UI
   ↓
8. UI shows success message ✓
```

### **Scenario: Dashboard needs latest weight**

```
1. Dashboard screen loads
   ↓
2. Dashboard calls: weightEntryService.getLatestEntry()
   ↓
3. Service calls: database.getLatestWeightEntry()
   ↓
4. Database generates SQL:
   SELECT * FROM weight_entries 
   ORDER BY date DESC 
   LIMIT 1
   ↓
5. SQLite reads from file, returns result
   ↓
6. Database returns WeightEntry object (type-safe)
   ↓
7. Service returns to Dashboard
   ↓
8. UI displays: "Current Weight: 180.5 lbs"
```

## Key Concepts

### **Type Safety**
```dart
// ✅ Correct - returns List<WeightEntry>
final entries = await service.getAllEntries();

// ❌ Wrong - compiler catches this error
final entries = await service.getAllEntries();
final weight = entries[0].name; // ERROR: WeightEntry has no 'name'
```

### **Reactive (Optional - for later)**
```dart
// Watch for changes - UI updates automatically
watchAllEntries().listen((entries) {
  setState(() {
    _entries = entries; // UI rebuilds when data changes
  });
});
```

### **Offline First**
- All data saves to device immediately
- No internet required
- Perfect for weight tracking (you log even without WiFi)

## Common Questions

**Q: Do I need to write SQL?**  
A: No! Drift generates it from Dart code.

**Q: Where is the database file stored?**  
A: On device storage (varies by OS, but managed by Drift).

**Q: Can I backup/restore data?**  
A: Yes - that's what CSV export in Settings does.

**Q: What if I need to change the database schema later?**  
A: Increment `schemaVersion` and add migration code.

**Q: Is SQLite secure?**  
A: Good for local data. For sensitive auth tokens, use secure storage packages.
